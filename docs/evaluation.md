# Сравнение и уверенность

Контрольные значения получены из данных магазинов, без самостоятельной ручной разметки фотографий организатором. Они могут быть неполными или расходиться с видимым на снимке. Поэтому метрики ниже измеряют согласованность с источником; учитывайте это ограничение в отчете.

## Протокол

Единица оценки — товар с одним объединенным результатом. До test зафиксируйте правило выбора от 1 до N ракурсов выбранного цветового варианта и применяйте его одинаково во всех подходах. Можно начать с опорного `primary_image`; если основное сравнение выполнено на одном фото, отдельно покажите работу выбранного сервиса с несколькими ракурсами. Полный второй прогон всех трех подходов на многовидовом входе не обязателен. Общие снимки с неподтвержденным цветом и фото других вариантов не добавляйте автоматически.

Используйте выданные validation/test без переноса товаров между ними. На validation выбирайте инструкции, тексты классов, пороги и подход. Затем зафиксируйте конфигурации и сравните все три подхода на **всем test** с одними и теми же изображениями и эталонами. Test не используется для подбора порогов после просмотра результатов.

Вход модели — фотографии товара и таксономия/ваши общие инструкции. Не передавайте ей эталон, название, категорию магазина, описание товара или путь файла с ответом. Если URL изображения раскрывает класс, передавайте содержимое файла. Служебные метаданные доступны для анализа срезов, но не для подсказки модели.

Код оценки и вызовов вы пишете самостоятельно. Сохраните точные версии данных/таксономии, идентификаторы изображений, предсказания, ошибки и конфигурации. Проверка на пустом или неполном test не считается полным сравнением.

## Что измерить

| Показатель | Что должно быть ясно из отчета |
| --- | --- |
| Категория | Accuracy на всех известных эталонных категориях; число объектов в знаменателе. Неопределенный ответ модели на известном эталоне считается ошибкой. |
| Визуальные признаки | Точность отдельно по каждому основному атрибуту и средняя по атрибутам. В знаменателе — все применимые известные эталоны; отказ модели не исключается из него. |
| Покрытие | Доля признаков, для которых модель дала допустимое известное значение, и доля полностью/частично размеченных товаров. |
| Отказы и неопределенность | Число ошибок API, некорректных ответов, неизвестных значений и случаев вне таксономии. Не смешивайте их в одну категорию без расшифровки. |
| Скорость | p50 и p95 времени на запрос товара с указанием числа фото; границы измерения, параллелизм и влияние повторов/ошибок. Отличайте вызов модели от полного пути API → БД. |
| Стоимость | Фактический расход и оценка на 1 000 товаров с указанием числа фото и допущений. |

Неприменимые признаки не входят в оценку распознавания их значения. Ошибочное заполнение неприменимого признака учитывайте отдельно. Эталонное `unknown` не превращайте в произвольный правильный класс: покажите поведение на таких случаях и размер этого среза. Не штрафуйте модель за допустимый признак только потому, что магазин его не указал. Если выбранный подход не решает какой-то атрибут, явно покажите потерю покрытия.

Сохраните результаты по товарам с перечнем входных фото в машинно читаемом виде и сводную таблицу трех подходов. Добавьте несколько разобранных удачных и ошибочных случаев со ссылками на идентификаторы; копировать изображения в публичный отчет можно только в рамках условий датасета. Необходим обоснованный выбор по совокупности качества, скорости, стоимости и надежности; минимального универсального порога качества заранее не задано.

## Confidence и общий score

Спроектируйте оценку надежности отдельных предсказаний и **общий score результата пайплайна**. Опишите диапазон, смысл, исходные сигналы и правила расчета. Укажите, как влияют неизвестная категория, неполные признаки, нарушения таксономии и технические сбои, и при каком условии требуется ручная проверка. Полезно показывать покрытие отдельно: высокий score одного найденного признака не должен создавать впечатление полной разметки.

Формула и формат полей остаются вашим решением. Не называйте score вероятностью правильности без проверки этого свойства. Самооценка VLM, вероятность класса у классификатора и сходство embeddings имеют разный смысл и не становятся сопоставимыми только из-за приведения к диапазону 0–1.

У Jev `Choice.confidence` вычисляется из распределения по вариантам и отличается от максимальной вероятности; определения приведены в [документации](https://docs.typesafe.ai/confidence). Для своего score проверьте на validation хотя бы, становится ли больше ошибок при снижении оценки. В отчете покажите связь score с качеством и долю отправляемых на проверку результатов. Полноценное исследование калибровки не требуется.
