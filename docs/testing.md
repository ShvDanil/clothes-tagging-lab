# Тестирование и сценарии сбоев

## Проверки каркаса

Обычный `pytest` проверяет инфраструктурные маршруты, обработку недоступности БД в readiness и наличие multipart-входа. `pytest -m integration` проверяет создание таблицы на PostgreSQL, JSONB, транзакционный rollback и ограничение уникальности. Они не доказывают, что разметка или идемпотентность API реализованы.

GitHub Actions запускает lint/format, эти тесты с PostgreSQL и сборку runtime-образа. Изображения, S3-доступ и платные ключи для исходного CI не требуются. Дополните workflow при необходимости, сохранив это свойство.

Проверки допуска 1–N файлов пока ожидают HTTP 501 от заготовки. После реализации замените эти ожидания проверками результата с подменой провайдера; тесты не должны обращаться к платной модели.

Через Docker можно выполнить и обычные тесты:

```bash
docker compose --profile test build tests
docker compose --profile test run --rm tests pytest -p no:cacheprovider -m 'not integration'
docker compose --profile test run --rm tests
```

## Сценарии для вашей реализации

Реализуйте воспроизводимые подмены провайдера/БД и тесты. Таблица задает ситуации и наблюдаемые свойства, но не фиксирует устройство моков, классов или точные HTTP-статусы вашего контракта.

| Ситуация | Что проверить |
| --- | --- |
| Валидные JPEG/PNG, известная категория | Допустимые значения, score, ответ связан с записью в PostgreSQL. |
| Одно фото и несколько ракурсов одного товара | Один объединенный результат и одна запись о товаре; происхождение учитывает использованные фото. |
| Превышено число фото или общий объем; повторяющиеся файлы | Ограничения и политика дублей соблюдаются до лишних платных вызовов. |
| Один файл поврежден или обработка одного ракурса не удалась; признаки противоречат друг другу | Соблюдается заявленная политика полного отказа или частичного результата; сбой не скрывается, общий deadline конечен. |
| Пустой файл, текст под расширением `.jpg`, поврежденный файл, превышение лимитов | Контролируемый отказ до платного вызова, отсутствие ложной успешной записи. |
| Одежда вне словаря, не одежда, несколько равнозначных предметов | Следование описанной политике неопределенности/отказа, без принудительного выдуманного класса. |
| Провайдер сначала отвечает временной ошибкой, затем корректно | Ограниченные повторы и успешный результат без дубля. |
| Постоянный timeout/5xx или сетевой сбой | Исчерпание конечного бюджета времени/попыток, понятный отказ, отсутствие зависания. |
| 429 с `Retry-After`, затем восстановление; слишком долгий `Retry-After` | Учет рекомендации и общего deadline, отсутствие неограниченного ожидания. |
| 401/403 или неверные параметры запроса провайдера | Отличие от временного сбоя, отсутствие бессмысленных повторов. |
| Некорректный JSON, чужое значение таксономии, неверный тип или несовместимый атрибут | Валидация; некорректная разметка не сохраняется как полноценная. |
| Только часть признаков распознана; модель «уверена» в неподтвержденном | Неизвестные признаки явно обозначены, score/покрытие и проверка соответствуют политике. |
| Ошибка БД при записи | Нет ответа об успешно сохраненном результате; транзакция не оставляет частичную запись. |
| Последовательный и конкурентный повтор, тот же ключ с другим набором фото | Заявленная политика идемпотентности, предсказуемый результат и отсутствие дублей. |

Проверяйте содержимое результата и состояние БД, а не только HTTP-код. Повторы должны тестироваться без реального ожидания десятков секунд. Реальные вызовы можно запускать вручную для экспериментов, но не при каждом push. Эталонные метрики и тесты надежности — разные проверки, нужны обе.
